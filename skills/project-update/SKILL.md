# 更新项目记录

让项目始终有一份最新、可信的现状，并且任何一条现状都能回答"它是什么时候、因为哪份材料变成这样的"。

**完成的标准：** `status.md` 反映了本次材料之后的最新情况，每一条都有来源；`log.md` 末尾为每份材料追加了一条；新的决策各有一页；与已有记录不一致之处要么已按规则更新并留痕，要么列在"待裁决的不一致"里。

**边界：** 只写 `projects/<项目>/`（不含 `reports/`，那是别的角色写的）。`projects/_index.md` 由引擎生成，不要改。材料里没有的内容不要补，不推测负责人、日期或结论。

## 项目目录

    projects/<项目>/status.md     现状，每次整页重写
    projects/<项目>/log.md        日志，只在末尾追加，绝不改动已有内容
    projects/<项目>/decisions/    决策记录，一项一页：NNNN-简短标题.md

## 步骤

1. 读 `_brief.md`、线程页、每份材料的 `source.md`。一次有多份材料时，**按材料日期从早到晚依次处理**。
2. 确定材料日期：优先用正文里写明的日期（会议开在哪天、报告截至哪天），其次用 frontmatter 的 `doc_date`，都没有才用采集日期，并在日志里注明"材料未标日期"。
3. 项目目录不存在就是新项目：新建 `status.md`、`log.md`。
4. 读现有的 `status.md`、`log.md` 和相关决策页，逐项对比材料带来的变化：进展、里程碑日期、blocker 的出现与解决、决策、行动项、风险。
5. 按"不一致的处理"判断每一处变化该更新还是该挂起。
6. 重写 `status.md`、追加 `log.md`、新建或更新决策页。格式见 `_skill/references/formats.md`，动笔前先读它。

## 不一致的处理

| 情况 | 做法 |
|---|---|
| 材料日期晚于 `status.md` 的 `as_of` | 以新材料为准更新现状；日志里逐条记"原为 X，现为 Y" |
| 材料日期早于 `as_of`，且与现状冲突 | 不覆盖现状。写进"待裁决的不一致"：两边各说什么、各自的来源和日期 |
| 日期相近的两份材料互相矛盾，分不清哪个更权威 | 同上 |
| 材料与现状一致 | 现状不变；材料本身仍在日志里留一条 |
| 决策被推翻 | 旧决策页 `status` 改为 `superseded` 并填 `superseded_by`，另建新页；不删除旧页 |

用户在线程里对某条不一致做了裁决时，按他的裁决更新现状，在日志里记"经用户确认"，并把它从"待裁决的不一致"里移除。

## 检查清单

- [ ] `status.md` 的 frontmatter 有 `type: project-status`、`project`、`as_of`、`description`、`aliases`、`health`、`sources`
- [ ] `as_of` 是所依据的最新材料的日期，不是今天
- [ ] 有未解决的 blocker 或里程碑延期时，`health` 不是 green
- [ ] 现状里每一条末尾都有来源链接
- [ ] 已解决的 blocker、已完成的行动项已从现状移出，并在日志里记了一笔
- [ ] 行动项没写负责人或期限的标"未指定"，没有编造
- [ ] `log.md` 只是末尾多了内容，已有内容一字未动
- [ ] 没有内容的小节写"（无）"，没有删掉小节

## 容易出错的地方

| 发生过的事 | 规则 |
|---|---|
| 一封日期更早的邮件说上线是 12-08，把现状里的 12-15 覆盖了 | 先比日期。早于 `as_of` 的冲突信息进"待裁决的不一致" |
| 把今天的日期写成了 `as_of` | `as_of` 取材料日期 |
| 纪要里说"下周完成"，被写成了一个具体日期 | 能从会议日期确定算出来才写日期，否则照原文写并标"未指定具体日期" |
| 重写现状时丢了仍然有效的旧风险条目 | 重写前逐条过一遍旧现状：仍有效的保留，过时的移出并记日志 |

## 报告

摘要不超过 300 字，用普通段落：这份材料带来的变化（进展、日期变更、blocker 的出现与解决、新决策）；有"待裁决的不一致"时，把问题原样写在这里请用户裁决。报告的 `status` 写 `done`——记录已更新，只是有问题等回答。
