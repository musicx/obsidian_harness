# 写项目汇报

读者没有跟过这个项目的日常，读这份汇报是为了知道现在怎么样、有什么需要他做。

**完成的标准：** `projects/<项目>/reports/` 下有一份新汇报；里面每条事实都能在项目记录里找到并带链接；"待裁决的不一致"和需要决策的事项没有被遗漏或淡化；对照 writing 自查过。

**边界：** 只写 `projects/<项目>/reports/`。现状、日志、决策是别的角色维护的，只读。项目记录里没有的内容不写——包括你觉得"应该有"的背景、原因和预测。

## 步骤

1. **弄清要求。** 读线程页：受众是谁、要多长、覆盖哪段时间、有没有指定的结构。这次是不是对上一版的修改意见——是的话读上一版，只按意见改。
2. **确定范围。** 用户指定了时间范围就照办。没指定：看 `reports/` 里最新一份的 `date`，覆盖此后的变化；从未有过汇报就覆盖全部。
3. **读记录。** `status.md` 全文；`log.md` 中范围内的条目；这段时间涉及的决策页。
4. **列要点。** 在 `_scratch/claims.md` 里先列出打算写进汇报的每条事实及其出处（这个文件不会被保存）。找不到出处的不写。然后挑出读者最需要知道的三到五件事。
5. **成文**，格式见下。
6. **自查。** 对照 `_skills/writing/SKILL.md` 第 6 步过一遍，体裁参考读 `_skills/writing/references/report.md`；再逐条核对数字、日期、人名与项目记录一致。

## 汇报的结构

默认结构如下。用户要求了篇幅或结构时以用户为准；给管理层的短汇报把"需要决策或支持的事项"提到最前面。

    ---
    type: report
    project: <项目名>
    date: YYYY-MM-DD
    period: 起始日期 ~ 截止日期
    audience: <受众；用户没说就写"未指定">
    sources: ["[[projects/<项目>/status]]", "[[projects/<项目>/log]]"]
    ---
    # <项目名> 进展汇报（截至 YYYY-MM-DD）

    一句话结论：整体状态，加上读者最该知道的一件事。

    ## 需要决策或支持的事项
    ## 本期进展
    ## 里程碑与时间变化
    ## 当前 Blocker 与风险
    ## 下一步

    ## 来源
    本汇报依据的页面清单。

- 每条事实后面链接出处，用完整路径：`（[[projects/<项目>/status|现状]]）`、`（[[projects/<项目>/decisions/0002-…|决策 0002]]）`。
- 里程碑用表格：里程碑、原计划、当前预计、状态。
- `status.md` 里有"待裁决的不一致"时，如实写进"需要决策或支持的事项"，写明两种说法各自的来源，不要自己选一个。
- 没有内容的小节整节删掉。
- 文件名：`YYYY-MM-DD <标题>.md`。修改上一版时**新建** ` v2`、` v3`，不覆盖旧文件。

## 检查清单

- [ ] 第一段就能让读者知道项目状态和最重要的一件事
- [ ] 每条事实有出处链接，且与项目记录逐字段一致
- [ ] 所有未解决的 blocker 和待裁决的不一致都出现在汇报里
- [ ] 没有项目记录以外的内容（背景知识、原因推测、乐观的预测）
- [ ] 修改版是新文件，旧版还在

## 容易出错的地方

| 发生过的事 | 规则 |
|---|---|
| 状态是 yellow，汇报读起来一切顺利 | 结论句直接写出状态和原因 |
| 把行动项原样抄了十几条 | "下一步"只写对读者有意义的三五条 |
| 用户说"压缩到一页"，结果删掉了需要决策的事项 | 压缩时先保决策事项和 blocker，再保里程碑表，最后才是进展细节 |
| 为了显得完整，补了一段项目背景 | 读者要的是变化。背景一句话带过，或链接到现状页 |

## 报告

`_report.md` 摘要不超过 200 字，用普通段落：汇报的一句话结论；需要用户决策的事项；这是第几版、相对上一版改了什么。
