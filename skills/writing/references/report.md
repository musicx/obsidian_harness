# 汇报、方案和技术报告

写给领导和同事的东西读这一份：进展汇报、周报、方案与提案、调研与技术报告、复盘、决策备忘、请示邮件。中英文通用；英文的行文习惯另见 `en.md` 最后一节。

这类文章的读者不是来欣赏的，是来做事的。领导读到"够了"就停，他要的是结论、要他做什么、风险在哪、花多少钱和时间。同事要能照着动手。跨部门的读者没有你的上下文。

## 动笔前先答五个问题

答不出来就先别写，回去想清楚或补材料。答案不必写进正文，但正文的结构由它们决定。

1. **读者是谁，读完要他做什么？** 知道、决定、批准、还是动手。一篇只服务一个主要读者。
2. **一句话结论是什么？** 电梯里只够说一句时说的那句。写不出，说明还没想清楚。
3. **他读到结论后最先问的三个问题是什么？** 这三个问题就是正文的三节。
4. **我要他给什么？** 决策、资源、期限，具体到能用"同意"或"不同意"回复。
5. **我有多大把握，最不确定的是哪一处？**

然后做减法。手里有二十件事，汇报只交三到五件，按这个顺序留：读者做决定必须知道的；有风险或需要支援的；体现判断而不只是执行的；有数字支撑的。日常执行类的进附录或不写。

## 结构

**先写速读层，再填细节。** 先把标题、第一段和每一节的首句写出来，只读这几句，看能不能回答"做了什么、为什么是现在、怎么做、代价和风险、要读者决定什么"。答不上来就改这一层，不要急着写正文。

**标题写成结论。** `关于缓存方案的调研报告` → `建议缓存从 Redis 单机换成集群，预计月成本增加 2000 元`。纯信息类的至少写清对象和时间：`数据平台 11 月第 2 周进展`。

**第一段把话说完。** 结论、要读者做的事、最关键的一个依据或数字、期限。读者只看这一段也能做决定。只保留会改变读者是否同意的那部分理由。素材里没有答复期限、负责人这类必需项时，写 `[待填：答复期限]`，不省略也不代填。

**背景只写读者不知道而又必须知道的。** 顺序是：他已经知道的情况（一句）→ 发生了什么变化 → 由此产生的问题 → 你的回答。汇报里回答放最前，前三项压成两三句垫在后面。

**正文按读者的问题排，不按你做事的先后排。** 每一节回答一个问题，节的第一句就是这一节的结论，后面是依据。同一层的几点要回答同一个问题（都是"为什么"或都是"怎么做"），互不重叠。

**小标题。** 汇报、提案、调研报告的小标题写成结论，连起来读就是摘要：`成本分析` → `集群方案每月多花 2000 元，可以少一次全站故障`。设计文档这类会被反复更新、按目录查找的长文档，小标题用短的主题词，结论放在节的第一句。

**每条事项写明要读者做什么：** 知悉、决策，还是支援。需要决策和支援的单独成节放在前面，一条一件事，写明希望谁在什么时候之前答复。

**细节往哪放。** 对每段细节问一句：删掉它，读者的决定会不会变？会变的留在正文，紧跟它支撑的结论；只影响执行的进附录，正文留一句指路；只用来复查事实的给链接；都不影响的删掉。

## 常见类型的骨架

用户给了结构就照用户的。没给时用下面的默认骨架，没有内容的节整节删掉。

| 类型 | 骨架 |
|---|---|
| 进展汇报、周报 | 一句话状态（顺利 / 有风险 / 受阻，加原因）→ 需要决策或支持 → 本期成果 → 风险与阻塞 → 下一步 |
| 方案、提案 | 建议 → 为什么是现在 → 方案与备选（对比表，推荐的放第一行，没选的写明原因）→ 成本和收益 → 风险 → 需要的决策 |
| 调研、技术报告 | 结论 → 口径与方法（一段）→ 发现（每条一个结论句加证据）→ 结论可能错在哪 → 建议 |
| 复盘 | 影响（谁、多久、多大）→ 现在是否已经止住 → 时间线 → 原因 → 已经做的 → 接下来做的 |
| 决策备忘 | 决定了什么 → 背景 → 考虑过的选项 → 选它的理由 → 带来的后果 |
| 请示邮件、IM | 第一句就是请求，第二句是期限，然后才是原因 |

## 坏消息

延期、未达标、事故、被否决，以及"卡了两周还没动"这种正在变成坏消息的事，按下面写，不当成普通条目塞进第三段。

- **先判断能不能等到下次例行汇报。** 它影响别人的排期或决定、读者可能先从别处听说、拖下去损失会扩大、要上级出面才能挽回，占一条就建议单独立刻报，并在交付说明里告诉作者。
- **第一句就是坏消息本身，带准确的数。** `进度略有滞后` → `支付模块延期两周，原定 8 月 15 日上线，现在预计 8 月 29 日`。
- **影响面写全：** 谁受影响、多大、到什么时候、能不能挽回；同时写明哪些没受影响、有没有对外承诺过。
- **给方案，至少两个，标出推荐。** 各自的代价、需要的支持、需要谁在什么时候之前拍板。只报问题不给方案，等于把问题交给读者。
- **给新日期时，同时说明这次凭什么准。**
- **归因写事实，不写评价。** `三方一直不给接口` → `三方接口 7 月 20 日交付，比约定晚 8 天`。自己的失误写具体错在哪、已经改了什么，一句就够，不写"能力不足"。
- 读者多半还要向上转述。篇幅长时在最前面给一个四五行、可以直接转发的版本：变化、原因、影响、处置。

## 写法

- **写成果，不写活动。** `完成了接口联调` → `联调通过，P99 延迟从 800 毫秒降到 120 毫秒`。
- **推理写成段落，罗列才用列表。** 要点列表会把"因为、所以、但是"丢掉，读者看到三条并列的短语，看不到它们之间的关系。原因、取舍、判断写成完整的句子；并列的事项、步骤、选项对比才用列表和表格。
- **每个数字带分母、口径和对照。** `多数企业` → `951 家里的 7%`；哪天、哪个环境、什么单位；现值和基线一起给（`42%，2017 年是 29%`），读者才知道它算高算低。
- **形容词换成数字，换不出来就留空位。** "显著提升""大幅优化""有效推进"都要换成从多少到多少。素材里没有这个数时写 `[待填：具体数字]`，绝不代填。
- **"发现"和"认为"分开写。** 前者跟着数据，后者跟着判断。混在一段里，整段的可信度按最弱的那句算。先给数字再给解释。两件事同时发生不写成因果。
- **调研结论要自己先反驳一遍。** 列出可能的其他解释；说明哪些已经排除、怎么排除的；老实写出没排除掉的；据此把结论降到证据撑得住的程度。
- **称呼和承诺跟着作者走。** 对上级用"您"还是"你"，照作者的样文；没有样文时用"您"。素材里作者没有答应过的事（"我全程支持""我负责培训"）不替他答应，确有必要时写进交付说明请他确认。
- **不写表态和客套。** "在领导的关心和支持下""高度重视""积极推进""后续将持续跟进"全删。建议就写"建议……，理由是……"。
- **写清楚不做什么。** 范围之外的、这期放弃的、明确不建议的，各用一句话带理由。
- **不把写作过程写进正文。** "根据提供的材料""素材里没有提到"读者看不懂，他手里没有你的素材。写事实的状态："未核实""目前没有数据""待某某确认"。
- **压缩篇幅时按这个顺序保留：** 需要决策的事项 → 风险和阻塞 → 结论及其依据 → 进展细节。

## 交稿前

- 只读标题、第一段和各节首句，能不能复述全文？不能就回去改这几处，不是改正文。
- 读者读完第一段能不能做决定？
- 每一条"需要支持"，读者能不能用一个词回复？
- 换成一个刚看到坏消息、心情不好的领导来读：他会不会觉得你在瞒、在推责？他读完知不知道要做什么？
- 状态是黄或红时，全文读起来是不是仍然像"一切顺利"？
- 这段话换一个人、换一个项目照样成立吗？成立就是没有信息，补事实或删掉。
