# work_sheet 用户故事

状态：初稿（2026-11-13）。设计文档 [design.md](design.md) 以本文为准绳：每个里程碑的验收都对应这里的故事。

标注说明：**【原始】** 是你提出的场景，**【扩充】** 是我为了让原始场景在日常使用中走得通而补充的，可以删减。

## 1. 使用者与通用操作方式

使用者只有一个：我，一个需要持续积累技术知识、同时跟进多个项目的人。我只在 Obsidian 里操作，不碰命令行。

所有故事共用同一套操作习惯：

1. **提要求**：在 `inbox/` 新建一页，用自然语言写想要什么。材料用三种方式之一给出：贴 URL、把文件拖进这一页（Obsidian 会存为附件）、写本机文件路径。不需要记角色名，也不需要写 `@`；想指定角色时才写 `@角色`。
2. **发送**：执行 Obsidian 的 "Commit-and-sync" 命令。没同步之前，系统看不到任何东西，可以放心慢慢写。
3. **看回执**：几分钟内，系统在这一页我写的内容下面追加一个任务块，表示已接单。
4. **看结果**：任务结束后，同一个任务块里出现结果摘要和产出文档的链接；系统有疑问时也在这里提问。
5. **继续对话**：我在同一页往下写追问、修改意见或回答，再同步一次。一页 inbox 就是一个对话线程。
6. **看全局**：打开看板，能看到所有任务在哪一列，可以拖卡片来取消或重跑。

## 2. 知识类故事

### K0 逐步积累"我们的做法" 【扩充】

作为使用者，我没有现成的方法文档，想在日常使用中把"我们现在怎么做 X"一点点记下来，以便后续"对照我们现有做法"时有东西可比。

- 我怎么做：inbox 页里用自己的话写"我们现在做 X 的方式是……"，可以很粗略；或者在 K2 的结果里采纳系统起草的初稿。
- 系统怎么做：整理成一页**我方文档**（归我所有，系统此后不擅自改），编入知识库目录；内容只来自我写的话，不替我补充我没说过的做法。
- 验收：我方文档里没有我没说过的内容；知识库目录里能找到它；问"我们现在怎么做 X"能引用到它。

新 vault 是空的，我方文档只能这样慢慢长出来，所以 K2 必须能处理"还没有对应的我方文档"的情况。

### K1 把一篇文章收进知识库 【原始】

作为使用者，我看到一篇好的技术文章，想让系统提炼要点并整合进知识库，以便以后能查到、能和别的知识关联起来。

- 我怎么做：inbox 新建一页，贴 URL 或拖入下载好的文件，写"整合进知识库"。
- 系统怎么做：保存原文的一份不可变副本；写一页来源摘要；把文中的概念、方法、工具并入已有的知识页（已有就补充，没有才新建）；更新目录和日志。
- 验收：
  - 原文副本存在，且之后不会被改动；
  - 来源摘要页列出核心观点，每条能定位到原文；
  - 新增或更新的知识页里，来自这篇文章的内容都带来源链接；
  - 没有为已存在的概念另建一页重复的；
  - 任务块里列出了新建和修改的页面。

### K2 对照现有做法，补充升级 【原始】

作为使用者，我想让系统把一篇文章的做法和我们现行的做法对比，找出差距并升级我们的文档，以便团队的方法能持续吸收外部的好做法。

- 我怎么做：inbox 页里给出文章，写"对比我们现有的 X 做法，补充升级"。
- 系统怎么做：先完成 K1；找到相关的我方文档；写一份**差异对照**——文章主张什么、我们现在怎么做、建议改什么、理由；然后：
  - 对系统自己维护的知识页，直接更新；
  - 对我方文档，只给出修改建议（改哪一段、改成什么），等我回复"采纳"（可以只采纳其中几条）后再落笔。
- 验收：
  - 差异对照页逐条列出差距，每条同时引用文章原文和我方文档的对应位置；
  - 我没有回复"采纳"之前，我方文档一字未动；
  - 采纳后，被改动的段落注明依据的来源；
  - 文章与我们做法一致、没有可升级之处时，系统明确说"无需修改"，而不是硬凑建议；
  - 还没有对应的我方文档时，系统明说"没有现行文档可比"，只做 K1，并可据文章起草一份我方文档的初稿供我确认（见 K0）。

### K3 以文章为起点，扩展研究一个方向 【原始】

作为使用者，我想让系统根据文章提到的某个方向去搜集更多资料，以便把一个概念的全貌补完整，而不只是一篇文章的视角。

- 我怎么做：inbox 页里给出文章，写"围绕文中的 X，搜集相关内容，完善这个方向"。
- 系统怎么做：先完成 K1；联网搜集与 X 相关的资料（原文同样保存副本）；把多个来源综合进 X 的知识页，写清各来源的共识、分歧和各自的适用条件。
- 验收：
  - X 的知识页引用了不止一个来源，且每个来源都有保存的副本；
  - 来源之间有矛盾时，页面里并列呈现并注明出处，没有悄悄选边；
  - 任务块里说明搜了什么、采用了哪些、舍弃了哪些及原因；
  - 搜集范围有上限（来源数量、运行时长），不会无止境地扩展。

### K4 一次交多份材料 【扩充】

作为使用者，我想在一页里贴多个链接或文件一起处理，以便攒了一批阅读材料时不用逐个建页。

- 系统怎么做：每份材料单独登记一个任务、单独保存副本和摘要；全部完成后在任务块里给出汇总。
- 验收：一份材料失败不影响其他材料；每份材料的结果单独可见。

### K5 材料拿不到 【扩充】

作为使用者，当链接需要登录、被反爬、文件格式不支持时，我想被明确告知，以便我换一种方式提供。

- 系统怎么做：不猜测内容，不拿搜索到的二手转述冒充原文；在任务块里说明哪份材料、为什么失败、建议我怎么提供（例如下载后拖进来）。
- 验收：失败的任务出现在看板的"需要我处理"一列；我补上文件再同步后，任务能接着做完。

### K6 向知识库和项目记录提问 【扩充】

作为使用者，我想直接问问题（"我们对 X 的结论是什么""A 项目现在卡在哪"），以便不用自己翻页面。

- 我怎么做：inbox 页里写问题。
- 系统怎么做：从知识库和项目记录里查找并作答；短答案直接写在任务块里，长答案另存一页并给链接。
- 验收：答案的每个论断带页面链接；知识库里没有依据时明说"没有记录"，不用模型自己的常识冒充知识库内容。

### K7 整理知识库 【扩充】

作为使用者，知识库用了一段时间后，我想让系统做一次清理，以便重复的页面被合并、挂着的分歧被处理、没人链接的页面重新连上。

- 我怎么做：inbox 页里写"整理一下知识库"或"检查有没有重复的概念"。
- 系统怎么做：先由程序做体检（名称相近的页面、被多个来源提到却没有页面的概念、孤儿页、缺少描述的页面、带分歧标记的页面、长期未更新的页面），再逐项处理有把握的，其余列给我。
- 验收：
  - 合并后的页面保留了两页的全部内容和出处，所有原来指向被合并页的链接都改到了保留页；
  - 名字相似但内容不同的页面没有被误并；
  - 拿不准的页面对出现在任务块的"需要你决定"里，而不是被悄悄处理；
  - 整理没有引入任何知识库之外的新内容。

### K8 专题综述 【扩充】

作为使用者，我想让系统把知识库里关于一个主题的内容串成一篇文档，以便系统地过一遍，或拿去做分享。

- 我怎么做：inbox 页里写"讲讲 X 的全貌""写一份关于 X 的综述，下周给团队分享"。
- 系统怎么做：读相关的概念页、来源页和我方文档，定一条主线，写成给没读过这些材料的人看的文档。
- 验收：
  - 第一段读完就知道核心结论；
  - 每个论断带出处；只有一个来源支持的说法写明"据某来源"；
  - 来源之间的分歧并列呈现；
  - 文末列出知识库尚未覆盖的问题；
  - 知识库里相关内容太少时如实说明并建议先补充资料，而不是硬写。

## 3. 项目类故事

### P1 建立项目档案 【扩充】

作为使用者，我想让系统为我跟进的每个项目建一份档案，以便后续交入的材料知道归到哪里。

- 我怎么做：inbox 页里写"新建项目 A"，附上背景或第一份 PRD；或者直接交入材料并提到一个系统还不认识的项目名。
- 系统怎么做：建立项目目录和现状页；遇到不认识的项目名时先问我是新项目还是已有项目的别名，不自作主张。
- 验收：项目有唯一的名称和别名表；之后我用任何一个别名提到它，材料都归到同一个项目。

### P2 交入项目新材料，更新项目现状 【原始】

作为使用者，项目有了新的 PRD、进度报告或会议纪要，我想交给系统整理，以便随时有一份最新、可信的项目全貌。

- 我怎么做：inbox 新建一页，说明是哪个项目的什么材料，给出文件路径、附件或 URL。
- 系统怎么做：保存原文副本；提炼**进展、blocker、决策、行动项（谁、什么、何时）、风险、里程碑变化**；更新项目现状页；在项目日志里追加一条带日期的记录。
- 验收：
  - 现状页有"截至日期"，每一项都能追到来源材料；
  - 日期以材料本身的日期为准（会议开在哪天），不是交入的日期；
  - 已解决的 blocker 从现状里移出，但在日志里留有"何时出现、何时解决、依据什么"；
  - 行动项带负责人和期限，材料里没写的标"未指定"，不编造；
  - 任务块里用三五行概括这份材料带来的变化。

### P3 新材料与已有记录不一致 【扩充】

作为使用者，当新材料和之前的记录矛盾时（上线日期改了、范围变了、决策被推翻），我想清楚看到变化，以便不被悄悄覆盖的信息误导。

- 系统怎么做：更新现状的同时，在日志里记"原为 X，现为 Y，依据某材料"；被推翻的决策标注"已被某决策取代"而不是删除；分不清哪份更权威时（两份日期相近的材料互相矛盾）在任务块里问我。
- 验收：任何一条现状都能回答"它是什么时候、因为哪份材料变成这样的"。

### P4 生成项目最新汇报 【原始】

作为使用者，我想让系统生成某个项目的最新汇报文档（如 PPT），以便直接用于周会或向上汇报，只做少量修改。

- 我怎么做：inbox 页里写"生成 A 项目最新汇报，给管理层，10 页以内"。受众、篇幅、时间范围可写可不写。
- 系统怎么做：基于项目现状、上次汇报以来的日志和上一份汇报，写出 Markdown 汇报，存入该项目的汇报目录。
- 验收：
  - 汇报只包含项目记录里有依据的内容，末尾附来源清单；
  - 默认覆盖"上次汇报之后"的变化，并包含当前 blocker 和需要决策的事项；
  - 我提修改意见后（见 G2），产出新版本，旧版本保留。
- 格式：v0 只产出 Markdown。PPT 等特定格式是将来的扩展，通过给撰写角色挂载 skill 来提供具体做法，不在现阶段设计。

## 4. 通用故事

### G1 看进度、取消、重跑 【扩充】

作为使用者，我想在一个看板上看到所有任务的状态，并能取消或重跑，以便掌控系统在做什么、花了多少。

- 验收：看板按状态分列；把卡片拖到"取消"后同步，任务不再执行；把失败的卡片拖回"待执行"后同步，任务重跑。

### G2 追问与修改意见 【扩充】

作为使用者，我想在同一页里对结果提修改意见，以便不用重新描述背景。

- 我怎么做：在任务块下面接着写，同步。
- 验收：系统把它当作同一件事的延续，新任务能看到之前的要求和产出；不会把整页从头再做一遍。

### G3 系统向我提问 【扩充】

作为使用者，当我的要求有歧义时，我想被问一句，而不是让系统猜，以便少返工。

- 验收：问题出现在我写的那一页的任务块里，同时任务进入看板的"需要我处理"一列；我在页内回答并同步后任务继续。系统只在歧义会导致明显不同的结果时才问。

### G4 知道系统改了什么 【扩充】

作为使用者，我想知道每个任务新建和修改了哪些页面，以便信任知识库的内容，并在出错时能回退。

- 验收：任务块列出新建和修改的页面；知识库有一份只追加的操作日志；系统的每次改动是一次独立的 git 提交，可以单独回退。

### G5 阶段简报 【扩充】

作为使用者，我想定期看到这段时间系统里发生了什么，以便不用逐页翻也能跟上知识库和项目的变化。

- 我怎么做：inbox 页里写"这周有什么变化""做个回顾"。
- 系统怎么做：依据程序整理的变更记录，写一份简报：最值得注意的三件事、等我处理的事项、知识库的新收录和认识变化、各项目的变化。
- 验收：所有待采纳的建议和待裁决的不一致都列在"等你处理"里；每一项都链接到对应页面；写的是变化的实质，不是文件清单。

### G6 首页与导航 【扩充】

作为使用者，我想打开 vault 就看到该看的东西，以便不用记目录结构。

- 验收：
  - 首页列出需要我处理的任务、待采纳的建议、各项目的状态、最近收录的材料；
  - 知识库目录按主题分组，每个页面后面有一句话说明它讲什么；
  - 目录、日志、项目名册始终与实际页面一致，不需要任何人维护；
  - 任何一段知识都能点回它的来源，来源页能点回原文存档。

## 4.5 数据类故事（设计中）

对应设计文档 18.1 节，尚未实现。

### D1 问一个数据问题 【扩充】

作为使用者，我想用一句话问数据问题，以便不用自己写查询也能拿到可信的数字。

- 我怎么做：inbox 页里写"沪深 300 现在的市盈率在近十年处于什么分位？"
- 系统怎么做：判断问题需要哪个数据源，把任务定到有这份数据的机器上；在那里查数据字典、写查询、核对口径，给出结论。
- 验收：
  - 答案第一句就是结论，带数据截至日期；
  - 用到的每条查询都贴在笔记里，并且确实是执行过的；
  - 口径写清楚（哪张表、复权方式、样本范围）；
  - 数据不足以回答时明说缺什么，不拿相近的指标顶替；
  - 任务块里能看到是在哪台机器上跑的。

### D2 做一份数据分析 【扩充】

作为使用者，我想让系统围绕一个题目做多步的描述性分析（对比、排名、时间变化），以便直接拿来用在项目材料或知识库里。

- 验收：分析笔记有结论、方法与口径、结果表、查询、局限五部分；属于某个项目的存进该项目目录；我说"把这份分析收进知识库"时走正常的收录流程。

### D3 弄清一张表 【扩充】

作为使用者，我想让系统把某张表摸清楚并记下来，以便以后的分析不再重复踩同样的坑。

- 验收：数据字典里有这张表的一页，写明粒度、时间范围、关键字段的含义和单位、已知的问题；之后的分析任务会先读它。

### D4 数据在哪就在哪跑 【扩充】

作为使用者，我的数据分散在不同机器上，我想让分析自动在有数据的那台机器上执行，以便不用搬数据，也不用记哪份数据在哪。

- 验收：只有个人电脑有的数据，任务定给个人电脑，电脑没开时任务等待并写明在等谁；两台机器都没有的数据，系统直接告诉我；我明说在哪台机器上跑时以我说的为准。

## 5. 对两条原始故事的评估

两条都合理，也符合正常的操作习惯——"建一页、说一句话、给个材料"是最低的使用门槛。对照第二稿设计，它们暴露出五个缺口，已在设计第三稿中处理：

1. **故事里没有 `@`。** 你描述的都是自然语言的要求。所以自然语言是主入口，`@角色` 降为可选。
2. **材料是 URL、下载的文件或路径，不是 Markdown。** 需要一个把网页、PDF、Word 等转成 Markdown 并存档的采集步骤；它应该是确定性的程序，不是一个 agent。
3. **"项目"的含义变了。** 第二稿里的 `projects/` 是 agent 干活的工作区；故事 2 里的项目是你真实跟进的工作项目，有随时间变化的状态。两者要分开。
4. **特定格式的产出（如 PPT）。** v0 只出 Markdown；角色配置里留一个挂载 skill 的位置，将来由 skill 提供 PPT 等格式的具体做法。
5. **"补充升级"会改已有文档。** 需要区分我方文档和系统维护的知识页，前者只提建议。
